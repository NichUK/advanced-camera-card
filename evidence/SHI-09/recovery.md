# SHI-09 playback recovery evidence

2026-10-05 development checkpoint on feature/9-playback-recovery, stacked on feature/8-recording-continuation. Existing ACC issue/retry/watchdog facilities handle archive failures. Stable category/stage contexts discard upstream text and signed URLs. Fresh media_source/resolve_media renews supported HA authorization; an uncached signed HEAD distinguishes 401, 403, 404/410 and server failure before native decoding. Terminal failures require explicit retry. Network/timeouts retain bounded ACC backoff. Discovery retry keeps the current interval and historical instant, bypasses stale metadata, and never selects live video.

Controller tests cover stale failure suppression, uncached resolution and input clearing. Resolver tests cover stable HA adapter errors, actual Response status mapping, malformed destinations, transport rejection, a ten-second overall resolve/HEAD deadline and abort. Native MP4 error/source events distinguish unsupported format and decode failure without logging MediaError text. Existing visible-player liveness detection now observes archive frames; background/paused/ended video remains governed by its existing visibility and idle rules.

Four Chromium browser cases exercise rendered date selection, deleted media and explicit Retry, temporary server recovery, native unsupported PNG-as-MP4 rejection, and twenty 401/403/404/503 failures. Those twenty observed actionable UI failures have p95 58.8 ms (full samples in failure-timings.json). HTTP statuses are supplied by the existing service-worker media harness; this is browser UI latency, not measured production HA/NVR failure latency. Successful retry decodes synthetic H264 3840x2160 media and preserves the historical instant. It does not establish original Clear HEVC compatibility.
